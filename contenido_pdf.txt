1.	Contexto
DataGo	centraliza	la	gestión	de	
datos	maestros
	de	la	compañía.	Esta	prueba	te	pide	construir	el	
CRUD	completo
	(crear,	consultar,	modificar	y	retirar)	del
Cliente	Residencial
,	aplicando	las	reglas	de	negocio	de	las	secciones	siguientes.
No	se	requiere	autenticación	ni	manejo	de	roles	en	esta	prueba:	puedes	asumir	un	único	usuario	con	acceso	a	todas	las	operaciones.
2.	Especificaciones	técnicas	obligatorias
Frontend	y	Backend:
	puedes	trabajar	con	la	versión	de	Angular	y	de	.NET	que	ya	tengas	instalada;	no	es	necesario	actualizar	a	una	versión	específica.
Frontend:
	layout	responsivo	básico.	No	es	necesario	un	ajuste	mobile-first	pulido.
Backend:
	API	RESTful	con	Swagger/OpenAPI	habilitado	(la	documentación	automática	que	genera	.NET	es	suficiente).
Base	de	datos:
	relacional,	con	migraciones	reales	(no	un	modelo	solo	en	memoria).
Validaciones:
	las	reglas	de	negocio	deben	validarse	en	el	
backend
	(no	solo	en	el	formulario	Angular)	y	los	errores	deben	responder	con	mensajes	claros	y
códigos	HTTP	apropiados.
3.	Creación	de	Cliente	Residencial
3.1	Datos	Generales
Tratamiento	del	cliente:	
Sr/Sra
	o	
Empresa
.	Obligatorio.
Campos:	
Nombre	negocio
	(obligatorio,	editable),	
Razón	social	extendida
	(obligatorio,	editable),	
Nombre	completo
,	
Nombres
	y	
Apellidos
	(solo	lectura:
se	calculan	a	partir	del	tratamiento	y	la	razón	social	extendida).
Si	el	tratamiento	es	
Sr/Sra
:	Nombre	completo	=	nombres	y	apellidos;	Nombres	=	nombres	separados	por	coma;	Apellidos	=	apellidos	separados	por	coma.
Si	el	tratamiento	es	
Empresa
:	Nombre	completo,	Nombres	y	Apellidos	deben	contener	el	nombre	de	la	empresa.
Nota	1:
	el	enunciado	no	especifica	el	algoritmo	exacto	para	separar	"Razón	social	extendida"	en	nombres	y	apellidos	cuando	el	tratamiento	es	Sr/Sra.	Propone	un	criterio
razonable	y	documéntalo	como	supuesto.
Nota	2:
	Nombre	negocio	y	Razón	social	extendida	son	independientes	entre	sí:	Nombre	negocio	es	el	nombre	comercial	con	el	que	se	conoce	al	cliente	en	el	día	a	día;	Razón
social	extendida	es	su	nombre	o	denominación	legal	completa.
3.2	Datos	de	Comunicación
Campos:	teléfono	(con	extensión),	celular,	correo	electrónico.
Debe	existir	al	menos	un	teléfono	(fijo	o	celular).
El	correo	electrónico	es	obligatorio	únicamente	cuando	el	tipo	de	identificación	del	cliente	es	NIT.
Debe	validarse	que	no	se	ingresen	expresiones	"dummy".	El	enunciado	no	da	la	lista	completa:	propone	y	documenta	un	conjunto	razonable.
3.3	Dirección
Buscar	barrio	por	municipio	y/o	departamento	y/o	barrio.	Al	seleccionarlo,	se	autocompletan	(solo	lectura)	municipio,	departamento,	país	y	zona	de	transporte.
Checkbox	"dirección	rural":	si	se	marca,	se	habilita	un	único	campo	de	texto	libre.
Si	no	es	rural,	se	habilitan:	Vía	principal	(Letra,	Número,	Cardinalidad)	y	Vía	alimentadora	(Número,	Letra,	Cardinalidad,	Número,	Cardinalidad).
Si	no	es	rural,	debe	validarse	la	estructura	de	vía	principal	y	vía	alimentadora.	Debe	generarse	error	si	no	se	diligencian	los	datos	de	dirección.
Ejemplo	de	referencia
	(nomenclatura	urbana	colombiana),	solo	para	guiarte:	en	"Calle	10A	Sur	#	5-30",	la	
vía	principal
	es	"Calle	10"	con	Letra	"A"	y	Cardinalidad	"Sur";
la	
vía	alimentadora
	es	"5-30",	donde	el	primer	Número	(5)	identifica	la	vía	que	cruza	y	el	segundo	Número	(30)	es	la	placa/puerta	sobre	esa	vía.
3.4	Identificación	Fiscal
Tipo	de	documento	propuesto	según	el	tratamiento:	Sr/Sra	→	Cédula	de	Ciudadanía	(se	puede	cambiar	a	Cédula	de	Extranjería);	Empresa	→	NIT	(no	se	puede
modificar).
Validar	que	el	documento	tenga	la	estructura	correcta	según	las	reglas	colombianas.	El	enunciado	no	entrega	la	fórmula	(por	ejemplo,	el	dígito	de	verificación
del	NIT):	investígala	y	aplícala.
Error	específico	si	el	NIT	es	incorrecto.
Validar	que	el	número	de	documento	no	exista	ya	entre	los	"Clientes	Canal	Moderno"	(una	tabla	propia	mínima	—basta	con	tipo	y	número	de	documento—	que
puedes	precargar	con	datos	de	ejemplo).	Si	existe,	error	indicando	que	el	flujo	correcto	es	"Creación	clientes	canal	moderno".
3.5	Otros	campos	simples	de	creación
Centro
	(obligatorio,	texto	o	lista	simple).
Estrato
	(obligatorio,	lista	desplegable;	valores	típicos	1	a	6	según	la	clasificación	socioeconómica	colombiana).
3.6	Datos	que	se	fijan	en	la	creación
Clase	de	impuesto
	(de	solo	lectura):	se	deriva	del	tratamiento	—	Sr/Sra	→	
Persona	Natural

Persona	Jurídica

Condición	de	pago

	por	defecto.

El	listado	debe	permitir	buscar	por	
documento	de	identificación
,	
nombre	del	cliente
	o	
código	del	cliente
.
No	hay	más	regla	de	negocio	que	la	existencia	del	cliente:	si	se	consulta	uno	que	no	existe,	debe	generarse	el	error	
"El	cliente	a	consultar	no	existe"
,
no	una	respuesta	vacía	silenciosa.
Si	el	cliente	consultado	está	
bloqueado
	(ver	sección	6,	Retiro),	la	consulta	debe	mostrarlo	igual,	pero	incluyendo	una	advertencia	
"Cliente	bloqueado"
	en

Nota:
	el	enunciado	no	dice	si	un	cliente	retirado/bloqueado	debe	aparecer	en	el	listado	general	por	defecto	(además	de	en	la	consulta	puntual).	Toma	una	decisión
razonable	y	documéntala.
5.	Modificación	de	Cliente	Residencial
5.1	Campos	editables
Campo
Regla
Nombre	negocio
Editable	libremente.
Nombres	/	Apellidos
Editables.	La	
Razón	social	extendida
	se	actualiza	automáticamente	si	se	modifican.	El

	sigue	siendo

Razón	social	extendida

Barrio	/	Dirección
Editables,	con	el	mismo	comportamiento	de	autocompletado	que	en	creación.
Estrato	/	Centro
Editables.
Todos	los	demás	campos	del	cliente	(tratamiento,	tipo/número	de	identificación,	clase	de	impuesto,	condición	de	pago)	son	de	solo	lectura	y	no	forman	parte	del
alcance	de	código	de	esta	prueba.
5.2	Regla	de	bloqueo
Un	cliente	marcado	como	
bloqueado
	(ver	sección	6,	Retiro)	
no	puede	modificarse
.	Si	se	intenta,	la	operación	debe	rechazarse	con	un	error	claro.
6.	Retiro	de	Cliente	Residencial
El	retiro	es	una	
baja	lógica
:	marca	el	cliente	como	retirado/bloqueado	(por	ejemplo,	con	un	campo	de	fecha	de	retiro	o	un	indicador	booleano),	pero	el	registro
nunca	se	elimina	físicamente
	de	la	base	de	datos.
El	cliente	debe	existir.
No	se	debe	permitir	retirar	un	cliente	que	ya	está	retirado/bloqueado.
